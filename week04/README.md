# 4주차 · 복수상품·스프레드 전략 — 미국달러선물 근월물·차월물 평균회귀

**Team 05 | 제출일: 2026/11/13(금) 23:59까지**  
과제 기간: 2026/11/07(토)~11/13(금) · 중간 발표 자료: 11/12(목) 23:59까지

## 한눈에 보기

국내 미국달러선물 **2026년 11월물과 12월물의 가격 차이**를 대상으로 하는 자동매매 프로그램입니다. 두 월물이 같은 달러를 기초자산으로 한다는 점을 바탕으로, 가격 차이가 최근 평균에서 벗어났다가 다시 돌아오는지 검증합니다.

- **전략**: 장중에는 웹소켓 `KB`로 받은 `차월물 호가 중간값 - 근월물 호가 중간값`을 직전 24개 확정 5분봉 종가 스프레드의 평균·표준편차와 비교합니다. 평균보다 높으면 근월물 매수·차월물 매도, 낮으면 반대로 각 1계약 진입합니다. 과거봉 `compare`는 기존 봉 기반 체결 모형으로 별도 비교합니다.
- **진입 기준 비교**: A는 1.0σ, B는 기본 설계인 1.5σ, C는 2.0σ입니다. 같은 과거 자료에서 기준만 바꿔 비교하며, 세 전략이 동시에 계좌에 주문하지는 않습니다.
- **청산·위험관리**: 평균 회귀, 반대 방향 2.5σ 이탈, 합산손실 -10,000원, 보유 60분에 따라 청산합니다. 하루 최대 3회 진입 시도, 일일 손실 -30,000원에서 추가 진입 중단, 15:00 진입 중단·15:10 청산 시작·15:20 정리 목표를 적용합니다.
- **두 레그 관리**: 근월물 체결을 확인한 뒤 차월물을 주문합니다. 한쪽만 체결되거나 접수 상태가 불명확하면 정상 쌍 포지션과 구분해 처리합니다.
- **비용 비교**: 수수료와 슬리피지를 다르게 가정해 가격 차이의 회귀가 비용 반영 후에도 수익으로 남는지 확인합니다. 실제 계좌 수수료나 관측한 슬리피지를 사용한 실적은 아닙니다.
- **실행·기록**: 국내 모의 API를 사용하고, week03처럼 가격 JSON과 전략별 `journal_YYYYMMDD.jsonl`에 기록합니다. 별도의 거래·비교 CSV는 생성하지 않습니다.

```bash
cd week04
uv sync --locked
uv run python main.py compare                              # 저장된 과거 자료로 A/B/C 비교, 주문 없음
uv run python main.py check --env-file ../week02/.env       # 국내 모의 API 사전 조회, 주문 없음
uv run python main.py paper --env-file ../week02/.env       # 장중 모의계좌 주문 실행
```

> 이 README 하나가 4주차 보고서이자 실행 안내입니다. 수치는 `results/`의 저장 자료와 로그를 기준으로 작성했습니다.  
> **현재 완료한 실행은 공개 마스터 확인, 모의 API 사전 조회, 11/09 과거봉 리플레이와 비용 비교입니다. 모의계좌 주문·체결 실행과 화면 캡처는 아직 수행하지 않았습니다.**  
> 리플레이의 `FILL`과 손익은 체결 모형이 계산한 값입니다. 계좌의 실제 체결 실적으로 해석하지 않습니다.

## 1. 과제 요약

두 개 이상의 종목 또는 월물을 함께 관찰하고, 단일 종목의 방향 대신 **두 월물의 상대적인 가격 관계**로 매매 여부를 판단하는 것이 이번 과제의 목표입니다. 특히 두 주문의 접수·체결 상태를 각각 확인하고, 한쪽만 체결된 위험을 관리하는 데 초점을 두었습니다.

| 항목 | 이번 구현 | 확인 상태 |
| --- | --- | --- |
| 복수 월물 시세 | 11·12월물의 확정 5분봉을 같은 시각으로 결합 | 11/09 자료 수집·재생 완료 |
| 신호 판정 | 직전 24개 평균·표준편차를 이용한 상대 가격 이탈 | A/B/C 리플레이 완료 |
| 주문 처리 | 근월물 확인 후 차월물 주문, 각 레그 체결·잔고 대조 | 구현·자동 테스트, 계좌 실행 전 |
| 위험관리 | 단독 체결 정리, 접수 불명 중단, 손실·시간·일일 제한 | 구현·자동 테스트, 계좌 실행 전 |

## 2. 실행 방법

### 2-1. 설치

Python 3.11 이상과 uv가 필요합니다. API 호출부를 import하므로 `week02/`와 `week04/`를 함께 내려받아야 합니다.

```bash
cd week04
uv sync --locked
uv run python -m pytest -q       # 현재 자동 테스트 55개 통과
uv run python main.py --help
```

### 2-2. 인증 정보 설정

**국내 모의** APP Key·Secret을 사용합니다. week03의 해외 모의 키와 구분합니다. 두 방법 중 하나를 사용합니다.

```bash
# 방법 1: week04에 국내 모의 인증 설정
cp .env.example .env
# .env에 NH_PAPER_APP_KEY, NH_PAPER_APP_SECRET 입력
uv run python main.py check

# 방법 2: 기존 week02의 국내 모의 인증 파일을 그대로 읽기
uv run python main.py check --env-file ../week02/.env
```

환경변수가 `.env`보다 우선합니다. 키가 없으면 저장소 밖 `~/NHFutures/config/config.yaml`의 `paper.domestic` 설정을 읽습니다. 서버 주소는 모의 서버로 고정하며 실전 주문 명령은 지원하지 않습니다. 키·Secret·토큰·계좌 식별정보는 제출하지 않습니다.

### 2-3. 실행 모드 구분

| 명령 | 입력·시세 | 계좌 주문 | 기본 저장 위치 |
| --- | --- | --- | --- |
| `check` | 모의 API 현재가·호가·잔고·미체결 | 없음 | `results/check/journal_날짜.jsonl` |
| `stream-check` | 모의 웹소켓 KB 두 월물 호가 수신 확인 | 없음 | `results/check/journal_날짜.jsonl` |
| `collect` | 모의 API의 지정 날짜 과거 5분봉 | 없음 | `results/replay/bars_USD_날짜.json` |
| `compare` | 저장된 하루의 가격 JSON | 없음 | `results/replay/{A,B,C}/journal_날짜.jsonl` |
| `paper` | KB 웹소켓 호가·REST 통계용 확정봉·계좌 응답 | **모의계좌 주문** | `results/B/journal_날짜.jsonl` |

명령을 생략하면 조회 전용 `check`가 실행됩니다. `paper`는 [settings.toml](settings.toml)의 기본 기준 1.5σ로 동작합니다. `compare`의 A/B/C는 과거 자료 비교이며 세 전략이 계좌 주문을 나누어 실행하는 구조가 아닙니다.

같은 날짜의 리플레이를 다시 돌리면 해당 날짜 로그를 새로 계산합니다. 조회·모의계좌 기록은 날짜별 파일에 이어 씁니다. 다른 가정을 따로 보관하려면 `--output 폴더`를 지정합니다.

### 2-4. 과거 자료 수집과 A/B/C 리플레이

```bash
# 저장된 11/09 자료로 재현: 인증·API 접속 불필요
uv run python main.py compare

# 완료된 거래일의 과거 자료를 추가 수집: 국내 모의 키 필요
uv run python main.py collect --date 20261109 --env-file ../week02/.env

# 사용할 날짜의 파일을 직접 지정
uv run python main.py compare --input results/replay/bars_USD_20261109.json
```

가격 JSON 하나에 두 월물의 봉, 출처, 수집 API 응답을 함께 저장합니다. `bars_sha256`으로 저장 가격의 변경 여부를 확인합니다. 하루 자료씩 비교하며 현재 기본 입력은 11/09 자료입니다.

리플레이는 신호가 확정된 뒤 **다음 봉 시가**에 가정 체결합니다. 주문 시점의 스프레드가 이미 진입 범위로 돌아왔거나 손절 경계를 넘으면 진입하지 않습니다. 5분봉으로 관찰하므로 봉 내부의 가격 경로와 실제 주문 대기시간은 복원하지 못합니다.

### 2-5. 비용 비교 실행

```bash
# 비용을 제외한 비교 기준: 0틱·수수료 0원
uv run python main.py compare --slippage-ticks 0 --fee 0 --output results/replay/비용비교/0틱

# 기본 가정: 편도 1틱·수수료 0원
uv run python main.py compare

# 비용을 크게 둔 가정: 편도 2틱·수수료 500원
uv run python main.py compare --slippage-ticks 2 --fee 500 --output results/replay/비용비교/2틱_수수료500
```

`--slippage-ticks`와 `--fee`는 `compare`의 비용 가정을 바꾸는 옵션입니다. 실제 계좌 수수료를 조회하는 옵션이 아닙니다. 비용의 의미는 [3-5절](#3-5-비용-비교), 기록에서 확인한 결과는 [6-4절](#6-4-비용-가정별-결과)에 설명합니다.

비용 비교도 가격 자료는 동일하게 사용하며 별도의 더미 가격을 만들지 않습니다. 가정을 바꾸어도 기본 로그를 보존하려면 위 예처럼 `--output`을 구분해야 합니다.

### 2-6. 실시간 모의 트레이딩

```bash
# 주문 없이 먼저 조회
uv run python main.py check --env-file ../week02/.env

# 주문 없이 웹소켓 연결과 두 월물 호가 수신 확인(기본 10초)
uv run python main.py stream-check --seconds 10 --env-file ../week02/.env

# 평일 한국시간 09:00~15:20에 시작. 신호 발생 시 모의계좌 주문 전송
uv run python main.py paper --env-file ../week02/.env
```

| 시점 | 프로그램 동작 | 확인할 기록 |
| --- | --- | --- |
| 시작 | 종목·만기·승수, 대상 월물 잔고·미체결과 이전 실행 상태 확인 | `RUN_START`, `ACCOUNT_SNAPSHOT` |
| 시작 및 5분봉 확정 시점 | 별도 스레드에서 통계용 확정봉 갱신, 아직 미반영이면 재조회 | `REFERENCE_UPDATE`, `REFERENCE_ERROR` |
| 두 월물 호가 갱신 | 최신 호가 중간값으로 신호 계산, 봉 종가 신호를 기다리지 않음 | `QUOTE_PAIR`, `OBSERVATION`, `SKIP` |
| 진입 | 현재 호가·신호·횟수·일일 손실 재확인 후 두 레그 주문 | `ENTRY_ATTEMPT`, `ORDER_SUBMIT`, `FILL`, `PAIR_OPEN` |
| 보유 중 호가 갱신 및 약 0.25초 타이머 | 청산 가능 호가로 합산손익·시간·이탈 확인 | `MARK`, `PAIR_CLOSED` |
| 15:00 | 신규 진입 중단 | `SKIP` |
| 15:10부터 | 보유분 청산, 평평해지면 종료 가능 | `PAIR_CLOSED`, `RUN_END` |
| 15:20 | 잔여 상태 최종 확인, 미정리 시 경고·중단 | `RUN_END` 또는 `HALT` |

장 시작 전에 실행해 자동으로 기다리는 방식은 아닙니다. 거래량·호가·준비 구간·신호 조건이 충족되지 않으면 주문하지 않습니다. API 지연에 따라 감시 간격과 종료 처리는 늦어질 수 있습니다.

`paper`는 국내 주간 `KB` 두 월물을 구독합니다. 고정 5초 호가 조회나 봉 마감 후 5초 대기는 사용하지 않습니다. 통계는 직전 24개 확정 5분봉 종가로 갱신하고, 현재 봉 구간의 통계가 아직 준비되지 않았으면 신규 진입을 기다립니다. 같은 이탈에서 주문 시도가 반복되지 않도록 진입 시도 후에는 호가 z값이 진입 구간 안으로 돌아왔다가 다시 이탈해야 재시도합니다. 잔고 확인 후에도 최신 웹소켓 호가로 진입 조건을 재확인하므로, 그 사이 수렴하면 주문을 건너뜁니다.

연결이 끊기면 두 호가 캐시를 비우고 새 키로 재접속·재구독합니다. 새 연결에서 두 월물 호가를 다시 받아야 진입할 수 있으며, REST 호가로 자동 대체하지 않습니다. 보유 중 연결이 끊기거나 호가가 오래되면 기존 `STALE_FEED` 청산 처리를 적용합니다. 수신 스레드는 주문 확인 중에도 최신 호가를 갱신하며, 밀린 과거 호가를 순서대로 거래하지 않습니다.

조회 전용 `check`의 REST 호가 시간 초과는 1초 간격으로 최대 3회 재시도합니다(최초 포함 총 4회). 주문은 이 규칙으로 재전송하지 않습니다. 웹소켓 전환 후에도 주문·체결·잔고 확인은 REST이므로 이 단계의 지연까지 없어지는 것은 아닙니다.

`Ctrl+C`·`SIGTERM`·터미널 종료 신호를 받으면 현재 주문 확인을 마친 뒤 알려진 보유분의 청산을 시도합니다. 접수 상태가 불명확하면 추가 주문을 멈추고 HTS 대사를 요구합니다. 강제 종료나 통신 단절에서 청산을 보장하지는 않습니다.

같은 날 정상 재시작하면 `results/private/`의 횟수·실현손익·마지막 관측시각을 이어갑니다. 이전 상태가 보유 중·주문 중·불명확한 상태이면 자동 재개하지 않습니다. HTS의 두 월물 잔고·미체결과 로그를 대사해야 하며, 상태 파일을 지워 일일 제한을 초기화하지 않습니다.

### 3-2. 가설과 통계 계산

같은 달러를 기초자산으로 하는 두 월물은 환율 변화에 비슷하게 반응할 수 있지만, 만기·금리·수급 차이로 서로 다른 가격을 형성합니다. 최근 관계에서 크게 벗어난 가격 차이가 단기적으로 평균 수준으로 되돌아오는지 확인합니다.

```text
S(t) = 차월물 종가(t) - 근월물 종가(t)
μ(t) = 직전 24개 S의 평균                 # 현재 S(t) 제외
σ(t) = 직전 24개 S의 모집단 표준편차       # ddof=0
z(t) = (S(t) - μ(t)) / σ(t)
```

위 식은 과거봉 `compare`의 판정입니다. 웹소켓 `paper`는 `S = 차월물 호가 중간값 - 근월물 호가 중간값`을 사용하고, 평균·표준편차는 가장 최근의 확정 5분봉 24개로 계산합니다. 따라서 과거봉 리플레이 결과가 웹소켓 장중 진입 시각과 같다고 해석하지 않습니다.

스프레드는 음수여도 정상입니다. 예를 들어 -0.7원은 -0.9원보다 높은 값입니다. 매매 방향은 가격 차이의 절댓값이나 0이 아니라 **평균보다 높은지·낮은지**로 판단합니다.

같은 시작시각의 확정 5분봉만 결합하고, 진행 중 봉이나 중복 시각을 사용하지 않습니다. 결측·거래량 0이면 연속 관측치를 다시 모으고 전일 자료나 직전 가격으로 채우지 않습니다. 표준편차가 0이면 진입하지 않습니다. 과거봉 리플레이는 직전 24개와 현재 봉이 필요해 첫 판정이 11:05부터 가능합니다. 웹소켓 `paper`는 확정봉 24개가 준비된 11:00 이후 현재 호가로 판정할 수 있습니다. 통계의 가격은 봉 종가이며, 실시간 신호의 가격은 호가 중간값입니다.

평균회귀 여부는 검증할 가설입니다. 평균 자체가 이동하거나 월물 수급이 달라지면 이탈이 계속될 수 있습니다.

### 3-3. A/B/C 진입 기준 비교

| 비교안 | 진입 기준 | 확인하려는 점 |
| --- | --- | --- |
| A | 1.0σ | 작은 이탈에서도 기회를 확보하는 대신 비용·불필요한 진입이 늘어나는지 |
| B · 기본 설계 | 1.5σ | 기회 수와 이탈 크기 사이의 균형 |
| C | 2.0σ | 기회 감소와 큰 이탈이 지속되는 위험 |

| 신호 | 상대 가격 해석 | 근월물 | 차월물 | 기대하는 변화 |
| --- | --- | --- | --- | --- |
| `entry_z ≤ z < 2.5` | 차월물이 평균 관계보다 높음 | 매수 1 | 매도 1 | S 감소 |
| `-2.5 < z ≤ -entry_z` | 차월물이 평균 관계보다 낮음 | 매도 1 | 매수 1 | S 증가 |

이미 2.5σ 손절 경계를 넘은 관측치는 신규 진입에서 제외합니다. 주문 직전에도 신호 방향·이탈 크기를 다시 확인해, 신호 이후 수렴한 경우는 `REVERTED_BEFORE_ENTRY`로 기록합니다.

A/B/C 비교에서는 기본 비용 가정인 편도 1틱·수수료 0원을 동일하게 적용합니다. 이 비교는 진입 기준 차이를 보는 것이며, 비용 비교와 구분합니다.

### 3-4. 청산과 일일 위험관리

| 구분 | 기준 |
| --- | --- |
| 정상 청산 | 진입 당시 평균의 0.25σ 범위 도달 또는 평균 통과 |
| Z 손절 | 기대 방향과 반대로 진입 당시 평균에서 2.5σ 이상 이탈 |
| 금액 손절 | 양 레그 청산 추정손익 -10,000원 이하 |
| 시간 청산 | 첫 레그 체결 확인 후 60분 이상 |
| 일일 진입 | 최대 3회 시도. 거절·실패도 포함 |
| 일일 손실 | 당일 실현손익 + 보유분 청산 추정손익이 -30,000원 이하이면 청산·추가 진입 중단 |
| 장 종료 | 15:00 신규 진입 중단, 15:10 청산 시작, 15:20 정리 목표 |

평균·표준편차는 **진입 당시 값으로 고정**합니다. 진입 가설을 평가하기 쉽지만 새로운 평균으로의 변화에 늦게 대응할 수 있습니다. 평균을 계속 갱신하는 방식은 시장 변화에 적응하는 대신 보유 중 목표·손절선도 이동합니다. 두 방식의 성과 비교는 아직 수행하지 않았습니다.

실시간 신규 진입에는 양 레그 호가 폭 2틱 이하, 양방향 잔량 1 이상, 호가 경과 10초 이하, 두 월물 호가 시각 차 3초 이하를 요구합니다. 손익은 보유 방향의 반대 호가로 청산한다고 가정해 평가하며 설정 수수료도 반영합니다.

### 3-5. 비용 비교

**비용 비교의 목적은 스프레드가 평균으로 돌아오는 것과, 거래 비용을 반영하고도 수익이 남는 것을 구분하는 데 있습니다.** 작은 가격 차이를 거래하므로 두 레그의 진입·청산 비용이 결과에 영향을 줄 수 있습니다.

**슬리피지**는 기준 가격보다 불리하게 체결되는 차이입니다. 이번 리플레이에서는 다음 봉 시가를 기준으로 매수는 높은 가격, 매도는 낮은 가격에 체결한다고 가정합니다. 실제 호가·주문 대기열을 복원한 값은 아닙니다.

**수수료**는 레그 1계약을 한 번 매수하거나 매도할 때의 금액으로 설정합니다. 500원은 실제 계좌에서 확인한 요율이 아닌 비교를 위한 가정입니다.

한 쌍의 진입·청산에는 근월물 진입·차월물 진입·근월물 청산·차월물 청산의 **총 네 번 주문**이 필요합니다.

```text
한 쌍의 왕복 비용 가정
= 4 × (편도 슬리피지 틱 수 × 1,000원 + 레그당 편도 수수료)
```

| 비용 시나리오 | 편도 슬리피지 | 레그당 편도 수수료 | 한 쌍 왕복 비용 가정 | 목적 |
| --- | --- | --- | --- | --- |
| 비용 제외 기준 | 0틱 | 0원 | 0원 | 비용을 빼고 가격 변화만 관찰 |
| 기본 가정 | 1틱 | 0원 | 4,000원 | 불리한 체결 가격의 영향 확인. 수수료 미반영 |
| 비용 확대 가정 | 2틱 | 500원 | 10,000원 | 체결 비용 증가와 손실 제한의 상호작용 확인 |

슬리피지는 가정 체결가에 이미 반영하고, 그 체결가로 계산한 손익에서 수수료를 차감합니다. **체결가에 반영한 슬리피지를 최종 손익에서 다시 차감하지 않습니다.**

```text
레그별 손익 = 매수·매도 방향 × (청산 체결가 - 진입 체결가) × 10,000
합산 최종손익 = 근월물 손익 + 차월물 손익 - 왕복 수수료
```

비용 비교는 같은 원본 자료·같은 A/B/C 기준에 비용 가정만 바꿔 전략을 다시 실행합니다. 비용이 커지면 금액 손절에 먼저 도달할 수 있어 **청산 시각·청산 사유도 달라집니다.** 기존 손익에서 비용만 단순히 빼는 계산과 구분해야 합니다.

### 3-6. 두 레그 주문 보호

```text
양 월물 잔고·미체결 확인
→ 근월물 주문 → 체결 확인·잔고 대조
→ 차월물 주문 → 체결 확인·잔고 대조
→ 정상 쌍 포지션
```

| 상황 | 처리 |
| --- | --- |
| 근월물 거절·미체결 | 미체결 정리와 잔고 확인 후 차월물 주문 중단 |
| 근월물 체결 후 차월물의 명확한 실패 | 잔고 대조 후 근월물 반대주문으로 정리하고 신규 진입 중단 |
| 접수 응답 시간 초과·주문번호 누락 | 동일 주문 재전송·임의 반대주문 금지, 조회 기록 후 `UNKNOWN` 중단·HTS 대사 |
| 확인된 주문의 체결 지연 | 10초 확인 후 미체결 취소, 취소 중 체결 여부 재확인 |
| 한 레그 청산 후 나머지 실패 | 이미 청산한 레그를 반복 주문하지 않고 잔여 레그만 처리 |
| 계좌와 예상 장부 불일치 | 추가 주문 중단, 수동 주문·지연 반영·미체결 대사 |

두 주문은 동시에 체결되는 거래소 스프레드 주문이 아닙니다. 주문 사이에 단독 노출이 남습니다. 현재의 근월물 우선 방식은 대사하기 쉽지만 차월물 체결이 지연될 수 있으므로 모의 실행에서 확인해야 합니다.

## 4. 사용 API와 프로그램 구조

### 4-1. 실행 흐름

`main.py`에서 실행 모드를 고르고, `market.py`가 시세를 읽으면 `strategy.py`가 진입·청산을 판단합니다. `broker.py`가 레그별 주문과 쌍 포지션을 관리하고 `journal.py`가 각 단계를 기록합니다. `compare`에서는 실제 주문 대신 `replay.py`와 가상 장부를 사용합니다.

### 4-2. 사용 API

| API·자료 | 사용하는 곳과 목적 | 확인하는 값 |
| --- | --- | --- |
| 공개 종목 마스터 | 대상 월물 확인 후 `instruments.json`에 보관 | 코드·결제월·만기·계약 단위 |

| 웹소켓 `KB` (2종목) | `paper`의 실시간 진입 판정·청산 평가 | `sym`, `exch_tm`, `bid_pric_1`, `ask_pric_1`, `bid_qty_1`, `ask_qty_1` |

### 4-3. 기록 형식과 손익 확인

| 기록 | 내용 |
| --- | --- |
| `OBSERVATION`, `SIGNAL`, `SKIP` | 스프레드·평균·표준편차·진입 및 미진입 사유 |
| `WS_STATUS`, `QUOTE_PAIR`, `REFERENCE_UPDATE` | 웹소켓 상태, 판정에 사용한 두 호가·수신 시각, 통계 기준 갱신 |
| `ORDER_INTENT`, `ORDER_SUBMIT` | 주문 의도와 접수 결과 |
| `FILL`, `PAIR_OPEN` | 체결 확인과 양 레그 포지션 형성 |
| `PAIR_CLOSED` | 청산 사유, 근월물·차월물 손익, 수수료·최종손익·보유시간 |
| `UNWIND`, `HALT` | 단독 체결 정리 또는 자동 진행 중단 |
| `ACCOUNT_SNAPSHOT`, `RUN_END` | 잔고·미체결 대조와 종료 상태 |

`ORDER_SUBMIT`은 체결이 아닙니다. 모의계좌의 `FILL`은 주문내역의 체결번호·수량·가격을 확인한 기록이고, 리플레이의 `FILL`은 가정 체결입니다. 계좌 체결 시각 필드는 로컬에서 확인한 시각이며 원본 주문내역도 함께 남깁니다. 계좌·인증 식별 필드는 마스킹합니다.

```text
results/
  check/journal_20261110.jsonl
  replay/
    bars_USD_20261109.json
    A/journal_20261109.jsonl
    B/journal_20261109.jsonl
    C/journal_20261109.jsonl
    비용비교/
      0틱/{A,B,C}/journal_20261109.jsonl
      2틱_수수료500/{A,B,C}/journal_20261109.jsonl
```

가격 자료·출처·수집 API 응답은 가격 JSON 하나에, 거래·손익·미진입 사유는 날짜별 로그에 모읍니다. 비용 비교 결과도 같은 형식의 로그이며 더미 실행 기록이 아닙니다. 다만 체결은 모두 가정값입니다. `results/private/`의 잠금·재시작 상태는 운영에 필요한 파일로 Git 제출에서 제외합니다.

## 7. 결과 해석과 한계

### 7-1. 진입 기준 비교의 의미

A는 B/C보다 기회를 확보했지만 기본 비용을 상쇄하지 못했습니다. B는 한 신호가 주문 시점까지 유지되지 않았고, C는 거래 기회가 없었습니다. 기준을 높여 거래가 사라진 결과와 비용을 감수하고 거래한 결과를 구분해야 합니다. 하루의 최고 손익만으로 기준을 선택하지 않습니다.

### 7-2. 평균회귀와 비용 반영 수익의 차이

A의 두 거래는 평균 접근으로 청산됐지만 1틱 가정에서 모두 손실입니다. 관찰한 회귀 폭이 거래 비용보다 작을 수 있다는 사례입니다. 비용을 제외한 손익·비용 반영 손익·청산 사유를 함께 확인해야 합니다.

향후에는 진입 이탈의 크기뿐 아니라 예상 회귀 폭과 왕복 비용의 관계를 비교할 수 있습니다. 비용보다 넓은 괴리를 요구하면 비용을 감당할 여지가 생기지만 거래 기회도 줄어듭니다. 현재 코드에는 이러한 추가 진입 필터를 적용하지 않았습니다.

### 7-3. 체결 모형과 위험관리의 상호작용

비용 확대 가정은 단순히 수익을 줄이는 데 그치지 않고 금액 손절·보유시간을 바꿨습니다. 비교 시에는 손익과 함께 진입·청산 시각, 손절 사유, 거래 수를 확인해야 합니다. 특히 이번 2틱·500원 가정에서 진입 직후 손절한 결과를 실제 시장에서 관측한 위험으로 확대 해석하지 않습니다.

### 7-4. 검증 범위

- **기간**: 완료된 한 거래일만 분석했습니다. 다른 환율 흐름·만기 접근·유동성 조건을 대표하지 않습니다.
- **관측**: 같은 5분 구간의 종가를 결합했지만 두 월물의 마지막 체결이 같은 순간이었다는 뜻은 아닙니다.
- **봉 내부**: 5분봉 내부의 손실 한도 도달·회귀 순서와 평가손익 최대낙폭을 확인하지 못합니다.
- **주문 품질**: 리플레이는 대기열·실제 호가 잔량 소진·체결 지연·단독 체결 가능성을 복원하지 못합니다.
- **비용**: 수수료·슬리피지는 가정이며 실측 비용 검증은 남아 있습니다.
- **실행**: 자동 테스트와 사전 조회를 완료했지만 실제 모의 주문·체결·청산 검증은 남아 있습니다.

## 8. 오류 대응과 개선사항

### 8-1. 구현에 반영한 대응

| 문제 가능성 | 현재 대응 | 확인 범위 |
| --- | --- | --- |
| 두 월물 시각 불일치·결측 | 같은 구간만 결합, 결측 후 통계 준비 구간 재수집 | 저장 자료·자동 테스트 |
| 신호 이후 수렴 | 주문 직전 재검증과 미진입 사유 기록 | 리플레이에서 확인 |
| 한쪽만 체결 | 명확한 실패 시 잔여 포지션 정리·추가 진입 중단 | 자동 테스트 |
| 접수 여부 불명 | 재전송 없이 중단·대사 | 자동 테스트 |
| 취소와 체결 경합 | 취소 후 체결 여부 재확인 | 자동 테스트 |
| 일부 레그 청산 뒤 재시도 | 완료 레그를 제외하고 남은 레그만 처리 | 자동 테스트 |
| 중복 실행·재시작 제한 초기화 | 잠금과 날짜별 상태 보존, 비정상 상태 재개 차단 | 코드 구현, 실제 운영 검증 필요 |

위 항목을 실제 모의계좌에서 모두 경험하거나 해결했다고 주장하지 않습니다. 모의 주문 실행에서 같은 보호가 유지되는지 확인해야 합니다.

### 8-2. 추가 개선 후보

비용을 감당할 회귀 폭이 있는지 확인하는 필터, 차월물 유동성을 먼저 고려하는 주문 순서, 이동 평균 청산 방식, 관측·위험 감시 간격을 비교할 수 있습니다. 각각 거래 기회·단독 노출·적응 속도·API 호출량에 영향을 주므로 근거 없이 함께 추가하지 않습니다.

## 9. 향후 계획

| 항목 | 다음에 확인할 내용 | 필요한 근거 |
| --- | --- | --- |
| 기간 확대 | 다른 날짜·환율 흐름·만기 접근에서도 A/B/C 신호가 유지되는지 | 동일 설정의 가격 JSON·날짜 로그 |
| 실제 모의 실행 | 양 레그 접수·체결·취소·청산이 계획대로 진행되는지 | 주문번호·체결내역·잔고·미체결 |
| 실측 비용 | 기준 호가와 체결가 차이, 계좌 수수료 | 주문 시점 호가·실제 체결가·적용 요율 |
| 비용·진입 조건 비교 | 거래 기회·회귀 폭·손실과 비용의 균형 | 기준별 신호·미진입·손익·청산 경로 |
| 종료 검증 | 두 월물 모두 잔고·미체결 0인지 | `RUN_END`와 HTS 화면 |
| 제출 보완 | 실시간 실행 결과와 분석·캡처 추가 | `results/B/`, `screenshots/` |

최종 기준은 수익이 가장 높은 설정만 고르는 대신 거래 기회, 손실 규모, 수렴 시간, 실제 체결 안정성을 함께 비교해 결정합니다.
