# 3주차 · 해외상품 전략 구현 — SGX 미니 원달러(MKU) EMA 추세추종 + ATR 검증

**제출일: 2026/11/06(금) 23:59 까지**

## 한눈에 보기

SGX 미니 원달러 선물(`MKUX26`) 야간장에 **EMA 9/21 교차 추세추종** 전략을 적용한 자동매매 봇입니다.
같은 신호로 **전략 A(기본형)** 와 **전략 B(ATR 필터를 더한 개선형)** 를 함께 돌려 비교합니다.

- **전략**: 확정된 5분봉에서 EMA 9 가 EMA 21 을 상향 돌파하면 매수, 하향 돌파하면 매도로 1계약 진입합니다.
  B 는 여기에 「ATR(14) ÷ 직전 20개 봉 ATR 평균이 0.90\~1.30」일 때만 진입하는 변동성 필터를 더합니다.
- **청산·위험 관리**: 손절 ATR × 1.5, 익절 ATR × 2 (A·B 같음), 반대 교차 시 청산만, 하루 최대 5회 진입, 그날 실현 손익 -25 USD 도달 시 신규 진입 중단(진입 전에만 판정하므로 하루 손실은 -25 를 넘을 수 있음, [3-4](#3-4-리스크-체크-진입-직전--traderbotpy) 참고). 05:30 이후 신규 진입 없음, 05:45부터 강제 청산.
- **실행 방식**: NH선물 Open API **해외 모의환경(paper)** 에서만 돕니다. 실전계좌 주문은 하지 않습니다.
  - **A**: 모의계좌에 실제 시장가 주문 → `trader.main --strategy A`
  - **B**: A 의 기록(봉·지표·체결)을 읽어 ATR 필터만 다르게 다시 계산, 주문 없음 → `trader.main --strategy B`
    모의계좌가 하나라 A·B 가 같이 주문하면 순포지션이 서로 상쇄되기 때문입니다.
  - 리플레이: 지난 야간장의 실제 분봉으로 가상 시계 실행, 주문 없음 → `--strategy AB --replay-date YYYYMMDD`
  - 봇 테스트: 합성 봉으로 서버·인증 없이 흐름만 점검 → `--strategy AB --bot-test`
- **실시간 시세**: 웹소켓 `FA`(해외 시세체결)로 손절·익절을 감시하고, 끊기면 REST 현재가로 대신합니다.
- **기록**: 신호·필터·주문·체결·손익·오류를 `results/` 에 JSONL 한 줄 한 이벤트로 남기고, 대시보드에서 A/B 를 나란히 봅니다.
- 2주차 코드(`backend`, `bot.clock`, `bot.journal`, 종료 신호 처리)는 **week02 에서 import** 해 그대로 씁니다.

```bash
uv sync && cp .env.example .env                              # 설치, .env 에 해외 모의 APP Key·Secret 입력
uv run python -m trader.main --strategy AB --replay-date 20261030   # 리플레이 (지난 야간장, 주문 없음)
uv run python -m trader.main --strategy A                    # 실시간 A (모의계좌 실주문)
uv run python -m trader.main --strategy B                    # 실시간 B (다른 터미널, 주문 없음)
```

## 1. 과제 요약

**과제:** NH선물 Open API 로 해외 선물 상품 하나에 대한 규칙 기반 전략을 구현하고, 실제로 실행한 기록으로 결과를 분석합니다.
수익률은 평가 기준이 아닙니다. 「계획한 대로 돌아갔는가 · API를 바르게 썼는가 · 결과를 설명할 수 있는가」를 봅니다.
이번 주는 기본형(A)과 개선형(B)을 **같은 봉·같은 코드**로 돌려, 필터 하나가 결과를 어떻게 바꾸는지 비교하는 것이 목표입니다.

| 필수 기능 | 이 과제에서 한 것 | 근거 |
| --- | --- | --- |
| 시세 수신 | 5분봉 경계마다 `chart_minute` 로 확정봉 조회, 보유 중 웹소켓 `FA` 체결(5초 넘게 끊기면 REST `price`) | `BAR`·`WS_STATUS` 이벤트, `trader/market.py`·`trader/realtime.py` |
| 신호 판정 | EMA 9/21 교차, B 는 ATR 비율 0.90\~1.30 필터 | `CROSS`·`ENTRY_SIGNAL`·`ATR_FILTER_BLOCK`, `trader/strategy.py` |
| 주문 처리 | 모의계좌 시장가 주문 → `order_history` 로 체결가 확인 → `open_interest` 로 잔고 교차 확인. 응답 없는 주문은 재전송 없이 내역 조회, 봉마다 잔고 맞춤, 청산 전 미체결 확인으로 중복 청산 방지([3-4-1](#3-4-1-주문-한-건-보호-접수--체결--잔고)) | `ORDER_SUBMIT`·`FILL`·`ORPHAN_POSITION`·`EXIT_WAIT_PENDING`, `trader/broker.py`·`trader/bot.py` |
| 위험 관리 | 진입 전 5개 체크, 손절 ATR×1.5·익절 ATR×2, 하루 5회, 일일 손실 -25 USD 시 진입 중단, 05:45 강제 청산 | `RISK_BLOCK`·`EXIT_TRIGGER`, `trader/bot.py` |
| 실행 기록 | 신호·필터·주문·체결·손익·오류를 한 줄 한 이벤트로 기록. 주문·체결·청산 기록은 쓰자마자 디스크까지 저장(`fsync`) | `results/{A,B}/journal_*.jsonl` |
| 전략 비교 | B 가 A 의 기록을 읽어 필터만 다르게 재계산, 같은 거래는 A 체결가 공유 | `fill_source`(`A`/`assumed`), `trader/recompute.py` |

## 2. 실행 방법

### 2-1. 설치

Python 3.11 이상과 [uv](https://docs.astral.sh/uv/) 가 필요합니다. `week03/` 폴더에서 실행합니다. `../week02/` 폴더가 함께 있어야 합니다(코드를 import).

```bash
brew install uv          # macOS (최초 1회. 이미 있다면 실행 X)
cd week03
uv sync                  # .venv 생성 + 의존성 설치
uv run pytest            # 35개 테스트 통과 확인
```

### 2-2. 인증 정보 설정

**해외 모의** APP Key·Secret 이 필요합니다. 국내 키(week02)와 다른 키이므로 이름과 파일을 나눴습니다. 계좌 비밀번호는 쓰지 않습니다.
실행하면 첫 줄에 `인증 정보: env` 또는 `인증 정보: config.yaml` 로 어느 쪽을 읽었는지 나옵니다(**환경변수가 우선**).

- 해외 모의 키는 리얼 HTS **[6128] REST API 신청** 화면에서 **해외 모의계좌를 골라** 신청하면 발급됩니다.
- Secret 은 32자입니다. 잘리거나 공백이 섞이면 토큰 발급이 거부됩니다(8-1절).

**방법 1. 환경변수 / `.env`** — `trader/credentials.py` 가 읽습니다. `.env` 는 `.gitignore` 에 있어 Git 에 올라가지 않습니다.
모의(paper) 키만 받으므로 이 방법으로는 실전 주문이 나갈 수 없습니다.

```bash
cp .env.example .env     # 열어서 NH_PAPER_OVERSEAS_APP_KEY, NH_PAPER_OVERSEAS_APP_SECRET 입력
# (선택) NH_PAPER_BASE_URL, NH_PAPER_WS_URL — 비우면 https://apidemo.futures.co.kr, wss://apidemo.futures.co.kr
```

**방법 2. 설정 파일** — 환경변수에 키가 없으면 week02 와 같이 저장소 밖 `~/NHFutures/config/config.yaml` 의 `paper.overseas` 를 읽습니다(형식은 [week02 README 2-2절](../week02/README.md#2-2-인증-정보-설정)).

### 2-3. 실행 모드 구분

**리플레이**는 지난 야간장의 실제 데이터로 전략을 다시 돌리고(주문 없음), **봇 테스트**는 합성 봉으로 프로그램 흐름만 점검합니다.
**실시간 모의 트레이딩**은 장중에 A 가 모의계좌로 실제 주문을 내고, B 는 A 의 기록을 따라 읽습니다. 네 기록은 섞지 않습니다.

| 구분 | 명령 (`uv run python -m trader.main` 뒤) | 데이터 | 주문 | 키 | 기록 |
| --- | --- | --- | --- | --- | --- |
| 리플레이 | `--strategy AB --replay-date YYYYMMDD` | 그날 분봉을 모의 서버에서 받음 | 없음 | 필요 | `results/replay/{A,B}/` |
| 봇 테스트 | `--strategy AB --bot-test` | 합성 봉 (`trader/synthetic.py`, 시드 고정) | 없음 | 불필요 | `results/bot-test/{A,B}/` |
| 실시간 DRY_RUN | A: `--strategy A --dry-run` / B: `--strategy B --dry-run` | 실시간 조회 | 없음 (기록만) | 필요 | `results/dry-run/{A,B}/` |
| 실시간 모의 | A: `--strategy A` / B: `--strategy B` | 실시간 조회 + 웹소켓 | **A 만 모의계좌 시장가** | 필요 | `results/{A,B}/` |

- 파일 이름은 `journal_YYYYMMDD.jsonl` 이고 날짜는 **장이 열린 날**입니다(11/03 20:50 \~ 11/04 06:15 장 → `journal_20261103.jsonl`).
- 기록의 `RUN_START.environment` 가 `paper` / `replay` / `bot-test` 로 구분됩니다.
- 실시간은 A·B 를 **각자 터미널**에서 돌립니다(`--strategy AB` 는 리플레이·봇 테스트 전용).

### 2-4. 리플레이·봇 테스트 (주문 없음)

#### 2-4-1. 리플레이: 지난 야간장으로 다시 돌리기 — `--replay-date` (모의 키 필요)

```bash
uv run python -m trader.main --strategy AB --replay-date 20261030   # 10/30(금) 20:50 ~ 10/31 06:15
```

시작할 때 그날 5분봉(지표 미리 채우기용 앞선 5일 포함)·1분봉을 모의 서버에서 한 번 받아 `results/replay/bars_MKUX26_<날짜>.json` 에 남기고,
**가상 시계**로 20:50\~06:15 를 몇 초 만에 돌립니다. A 가 끝나면 B 가 A 의 기록을 읽어 다시 계산합니다.

- 현재가 = 그 시각까지 확정된 마지막 1분봉 종가. 봉 안의 고가·저가는 보지 않아 손절·익절이 실제보다 늦게 잡힐 수 있습니다.
- 주문은 보내지 않고 체결가는 그때 현재가로 가정합니다. 잔고·미체결·주문가능수량 조회도 하지 않습니다.
- 미래 날짜·주말·아직 06:15 가 지나지 않은 장은 거절합니다. 봉이 0개인 날은 안내만 하고 끝나며 전에 남긴 기록은 지우지 않습니다.
- 같은 날짜로 다시 돌리면 그날 기록을 새로 씁니다(덮어씀).

#### 2-4-2. 봇 테스트: 합성 봉으로 흐름 점검 — `--bot-test` (서버 접속·인증 없음)


## 3. 전략과 매매 계획

### 3-1. 대상 상품

| 항목 | 값 | 근거 |
| --- | --- | --- |
| 종목 | SGX 미니 원달러(Mini SGX KRW/USD FX Futures) 2026-11 | REST 현재가 응답 종목명 |
| 종목코드 / 실시간 코드 | `MKUX26` / `MKUX26` | `overseas_price` 의 `occurs1_real_sym` |
| 거래소코드 | `FSGX` | `F` + 거래소 |

| 실제 거래 시간 (KST) | 주간 08:25\~20:35, **야간 20:50\~06:15** | 분봉으로 확인 (06:15\~08:25 거래 없음, 8-1절) |
| 가격대 | 0.744\~0.755 (10/26\~10/30 야간장 진입가) | 리플레이 기록 |

### 3-2. 가설

5분봉 EMA 9/21 교차는 짧은 추세의 시작을 잡는다. 다만 **변동성이 평소보다 너무 낮으면** 교차가 노이즈일 가능성이 크고,
**너무 높으면** 손절이 쉽게 맞는다. 그래서 B 는 ATR 이 평소(직전 20개 봉 평균) 대비 0.90\~1.30 배일 때만 진입한다.
A 와 B 의 차이(필터가 거른 신호의 손익)가 곧 이번 주 검증 데이터입니다.

### 3-3. 매매 규칙 (`trader/strategy.py` 와 1:1)

1. **확정봉만 사용**: 종료 시각이 지나지 않은 봉은 판단에 쓰지 않는다. 봉 마감 5초 뒤 조회.
2. **지표 미리 채우기**: 앞선 날 봉(최대 5일)으로 EMA·ATR 을 채워 20:50 첫 봉부터 판단한다.
3. **신호**: 직전 봉에서 EMA 9 ≤ EMA 21 이고 이번 봉에서 EMA 9 > EMA 21 → 매수. 반대면 매도. 행동은 가장 최근 확정봉에서만 낸다(밀린 봉은 기록만).
4. **B 필터**: 봉 마감 후 확정된 `ATR_t ÷ 평균(ATR_{t-20} … ATR_{t-1})` 이 0.90\~1.30(양끝 포함)일 때만 진입. 아니면 `ATR_FILTER_BLOCK`.
5. **손절·익절**: 진입 당시 ATR × 1.5 / × 2. **틱 맞춤은 둘 다 진입가 쪽으로** — 매수: 손절 올림·익절 내림 / 매도: 손절 내림·익절 올림.
   손절 거리가 1틱 미만이면 진입하지 않는다(`SKIP stop_below_1tick`, 1틱으로 늘리면 계획 손실을 넘기므로 배제).
6. **반대 교차**: ATR 필터와 무관하게 **청산만**. 반대로 바로 진입하지 않는다.
7. **재진입**: 청산 뒤 **새 교차**가 나올 때만.
8. **횟수·시간**: 하루 최대 5회 진입. 그날 실현 손익 합이 -25 USD 이하가 되면 신규 진입 중단(보유분은 원래 규칙대로 청산). 한도는 진입 직전에만 보므로 -25 에 닿기 전 마지막 진입이 손절되면 그만큼 한도를 넘는다. 신호 봉 종료가 05:30 이하일 때만 진입, 05:45부터 보유 중이면 강제 청산, 06:15 종료.

상태 흐름: `FLAT → (교차·필터·리스크 통과) → IN_LONG / IN_SHORT → (손절·익절·반대 교차·강제 청산) → FLAT`

### 3-4. 리스크 체크 (진입 직전 — `trader/bot.py`)

하나라도 실패하면 진입하지 않고 실패 항목마다 `RISK_BLOCK` 을 남깁니다.

| # | 체크 | 기준 |
| --- | --- | --- |
| 1 | 보유 없음 | `open_interest` 에 해당 종목 없음 (`NO_POSITION`) |
| 2 | 미체결 없음 | `order_history` 미체결 잔량 0 (`NO_PENDING`) |
| 3 | 증거금 | `orderable_quantity` 매수·매도 가능 수량 ≥ 1 (`ORDERABLE`) |
| 4 | 횟수 | 당일 진입 < 5 (`ENTRIES`) |
| 5 | 일일 손실 | 그날 청산된 거래 손익 합 > -25 USD (`DAILY_LOSS_LIMIT`) |

> **일일 손실 한도는 하루 손실의 상한이 아닙니다.** 5번 체크는 진입 직전에 *이미 청산된* 손익만 봅니다.
> 누적이 -25 보다 위면 진입이 허용되고, 그 거래가 손절되면 손절 금액만큼 -25 를 넘어 끝납니다.
> 그 뒤로는 신규 진입이 막힙니다. 즉 하루 최대 손실 ≈ -25 바로 위 + 손절 1회(+ 손절가보다 불리한 체결분)입니다.
>
> | 예: 10/27 (A·B) | 진입 직전 누적 | 판정 | 결과 | 거래 후 누적 |
> | --- | --- | --- | --- | --- |
> | 1번째 | 0 | 통과 | 손절 −12.5 | −12.5 |
> | 2번째 | −12.5 | 통과 | 손절 −10.0 | −22.5 |
> | 3번째 | −22.5 | 통과 (아직 −25 위) | −5.0 | **−27.5** |
> | 이후 교차 | −27.5 | `DAILY_LOSS_LIMIT` 차단 | — | — |
>
> 이 방식을 유지한 이유: 진입 판단만 바꾸고 보유 중인 포지션은 건드리지 않아, 손절·익절과 별개인 청산 경로를 새로 만들지 않습니다.
> 한도를 엄격히 지키려면 「누적 + 이번 거래 손절 예상 금액」으로 진입 전에 판정하거나, 평가 손익 포함 -25 도달 시 즉시 청산하는 방식이 필요합니다(8-3절 개선사항 후보).

### 3-4-1. 주문 한 건 보호 (접수 → 체결 → 잔고)

주문·체결·잔고 확인이 중간에 어긋나도 **포지션을 관리하지 않고 두는 경우**와 **같은 주문을 두 번 내는 경우**를 막습니다.

| 상황 | 처리 | 기록 |
| --- | --- | --- |
| 주문 응답을 못 받음 / 응답을 읽다 예외 | 다시 보내지 않고 주문내역에서 새 주문을 찾음. 못 찾으면 잔고 맞춤에 맡김 | `ORDER_SUBMIT recovered_from_timeout`, `ORDER_UNKNOWN` |
| 서버가 오류로 답함(`err_cd`, 업무 오류) | 접수 안 됨이 확실 → 진입 생략 / 청산은 다음 감시 때 재시도 | `ERROR` |
| 체결 확인 실패 후 늦게 체결 | 봉마다 잔고를 보고 관리 중인 거래가 없는데 포지션이 있으면 진입 1회로 세고 손절·익절가를 세워 관리 | `ORPHAN_POSITION`, `ENTRY_OPEN orphan=true` |
| 청산 전 미체결 남음 | 새 청산 주문을 내지 않고 3번(약 6초) 기다린 뒤 미체결 취소 → 잔고부터 다시 확인 (같은 청산이 두 번 체결돼 반대 포지션이 생기는 것 방지) | `EXIT_WAIT_PENDING`, `EXIT_CANCEL_PENDING` |
| 청산이 계속 확인 안 됨 | 손을 놓지 않고 계속 시도, 5번째부터 화면·기록에 경고(이후 30번마다) | `EXIT_STUCK` |
| 잔고와 관리 중인 거래가 다름 | 잔고 기준으로 청산 | `POSITION_MISMATCH` |
| 청산하려는데 이미 잔고 없음(HTS 에서 정리 등) | 거래 종료. 손익은 비우고, 일일 손실 한도에는 **손절가로 끝났다고 보고** 반영(보수적) | `ALREADY_FLAT`, `TRADE_CLOSED pnl_for_limit_usd` |
| 루프 한 바퀴에서 예상 못한 예외 | 기록하고 이어 감(보유 감시 유지). 연속 10번이면 멈추고 보유 경고 | `LOOP_ERROR`, `RUN_END stop_reason=CRASH` |
| 기록 쓰기 실패 | 청산 상태는 먼저 FLAT 으로 되돌림(같은 청산 반복 방지), 실패는 화면에 출력 | `[기록 실패]` |

- 재시작 복구의 근거인 `ORDER_SUBMIT`·`ORDER_CANCEL`·`FILL`·`ENTRY_OPEN`·`TRADE_CLOSED`·`RECOVER`·`RUN_END` 는 적은 뒤 `fsync` 로 디스크까지 내립니다.
- 재시작 시 진입 횟수는 `ENTRY_OPEN entry_counted=true` 로 셉니다(부분 체결·잔고 맞춤 포함). 일일 손익은 `pnl_usd`, 없으면 `pnl_for_limit_usd` 로 되살립니다.
- 점검: `tests/test_bot_safety.py` (응답 없는 주문 재전송 안 함, 잔고 맞춤, 미체결 대기·취소, 청산가 모를 때 한도 반영, 루프 격리 등 12개).

### 3-5. B 의 체결가 (주문하지 않으므로)

| `fill_source` | 언제 | 가격 |
| --- | --- | --- |
| `A` | A 가 같은 신호 봉·같은 방향으로 실제 진입 | A 의 실제 진입·청산 체결가 (진입 뒤 규칙이 같으므로 청산도 같음) |
| `assumed` | B 에만 있는 거래 (A 는 필터 없이 이미 보유 중이었거나 5회를 다 씀 등) | 진입: 신호 봉 종가 / 손절·익절: 다음 봉부터 5분봉 고가·저가, **같은 봉에서 둘 다 닿으면 손절**, 갭이면 시가 / 반대 교차: 그 봉 종가 / 강제 청산: 05:45 에 끝나는 봉 종가. 슬리피지 0 |

그래서 A·B 차이는 **ATR 필터가 거른 신호와 그 뒤로 달라진 보유 상태**에서만 생깁니다.

### 3-6. 미리 알고 있던 약점

- 손절·익절 틱 맞춤을 진입가 쪽으로 하므로 실제 손익비가 1.5 : 2 보다 나빠질 수 있다(예: 손절 5틱·익절 7틱).
- ATR 비율은 천천히 움직이는 ATR(14) 을 그 평균으로 나눈 값이라 1 근처에 모이기 쉽다. 0.90\~1.30 이 너무 넓으면 B 가 A 와 거의 같아진다.
- 야간장 MKU 는 거래가 얇아 5분봉 ATR 이 2\~4틱 수준이다. 틱 반올림의 영향이 크다.
- 일일 손실 한도(-25 USD)는 진입 전에만 판정하므로 하루 손실이 마지막 손절만큼 한도를 넘을 수 있다(리플레이 10/27·10/28 에 −27.5).
- 5일·하루 최대 5회라 표본이 작다. 결론보다 「필터가 무엇을 걸렀는가」를 본다.

- **신규/청산 구분 필드가 없습니다.** 보유 반대 방향 주문이 청산이므로, 청산 전 `open_interest` 로 방향·수량을 확인합니다.
- 주문 접수만으로 체결로 기록하지 않습니다 — `order_history` 의 체결가·체결수량이 있어야 `FILL`.

- 웹소켓: 키 발급 → 접속 → `session_init` → `FA` 구독(`RT_INIT`). 끊기면 뒤에서 계속 다시 접속하고, 5초 넘게 체결이 없으면 REST 현재가를 씁니다.

### 4-3. 기록 형식

`results/{A,B}/journal_YYYYMMDD.jsonl` — 한 줄이 한 이벤트(JSON). 공통 칸: `ts`(KST), `type`, `symbol`, `state`(`FLAT`/`IN_LONG`/`IN_SHORT`).

| type | 담긴 것 |
| --- | --- |
| `RUN_START` / `RUN_END` | 설정 스냅샷 전체, 환경, 세션(open·close·entry_cutoff·force_close) / 진입 횟수·보유, **멈춘 사유** `stop_reason`(`DEADLINE` 06:15 정상 · `CTRL_C` · `SIGHUP` · `SIGTERM` · `CRASH`). B 는 거래 수·공유/가정 거래 수·손익 |
| `RECOVER` / `WAIT_OPEN` | 시작 시 복구한 진입 횟수·당일 실현 손익(`realized_pnl`)·보유·미체결 / 장 시작 대기 |
| `BAR` | 확정봉 OHLCV + EMA 9·21, ATR, ATR 기준값, ATR 비율, 교차 여부 |
| `CROSS` | 교차 방향, 봉, ATR·ATR 비율 |
| `ENTRY_SIGNAL` | 방향, 손절·익절가와 틱, ATR, ATR 비율 |
| `SKIP` | 진입하지 않은 사유 (`MAX_ENTRIES`·`DAILY_LOSS_LIMIT`·`OUTSIDE_ENTRY_WINDOW`·`ATR_WARMUP`·`stop_below_1tick`) |
| `ATR_FILTER_BLOCK` | (B 만) ATR·기준값·비율·밴드 |
| `RISK_BLOCK` | 실패한 체크 항목, 값, 기준 |
| `ORDER_SUBMIT` / `ORDER_CANCEL` / `FILL` | 역할(ENTRY/EXIT), 요청·응답 원문, 주문번호(응답을 못 받아 내역에서 찾았으면 `recovered_from_timeout`) / 취소 / 체결가·수량(부분 체결이면 `partial`) |

| `EXIT_SIGNAL` / `EXIT_TRIGGER` | 반대 교차 / 사유(STOP·TAKE·FORCE), 트리거 가격 |
| `TRADE_CLOSED` | 진입가, 청산가, 틱 손익, USD 손익, 슬리피지(틱), `fill_source`. 청산가를 모르면 `pnl_usd` 는 비우고 한도용 `pnl_for_limit_usd`(손절가 기준) |
| `WS_STATUS` / `SOURCE_RESTART` | 웹소켓 접속 상태 / (B) A 기록이 새로 시작됨 |
| `ERROR` | API, 오류 종류, 메시지 코드, 메시지 (`CRASH` 는 traceback 포함, 봇 멈춤) |
| `ERROR` 의 봇 코드 | `LOOP_ERROR`(한 바퀴 예외, 이어 감) · `ORDER_UNKNOWN`(접수 여부 모름) · `FILL_TIMEOUT` · `FILL_UNCONFIRMED_BUT_HELD` · `ORPHAN_POSITION`(잔고 맞춤) · `EXIT_WAIT_PENDING` / `EXIT_CANCEL_PENDING`(중복 청산 방지) · `EXIT_STUCK`(청산 반복 실패 경고) · `POSITION_MISMATCH` · `ALREADY_FLAT` · `NOT_FLAT` · `POSITION_LEFT` — 처리 방식은 [3-4-1](#3-4-1-주문-한-건-보호-접수--체결--잔고) |

**② 10월 28일 — 수익 거래 차단과 손실 한도의 상호작용**

B는 ATR 비율 0.89를 기록한 22:25 숏 진입 신호를 차단하였다.

해당 거래는 A에서 +12.5 USD의 익절로 종료되었으므로 B는 수익 기회를 놓쳤다.

이후 B는 손절 거래가 누적되어 일일 손실 한도에 도달하였고, A에서 +22.5 USD를 기록한 03:40 롱 거래에도 진입할 수 없었다.

결과적으로 A는 +7.5 USD, B는 -27.5 USD를 기록했다.

**핵심은 ATR 필터가 특정 거래를 차단하는 효과뿐 아니라 이후 거래 기회와 손실 한도 도달 시점까지 변화시킨다는 점이다.**

**③ 10월 29일 — 손실 회피 효과와 추가 거래 손실이 공존**

B는 일부 저변동성·고변동성 교차 신호를 차단해 A의 손실 거래를 회피하였다.

그러나 A가 일일 최대 거래 횟수에 도달한 이후 B에서만 발생한 가정 거래가 손절로 종료되었다.

그 결과 A +2.5 USD, B 0.0 USD를 기록하였다.

**④ 10월 30일 — 수익 거래 차단**

B는 ATR 비율 0.87인 02:00 숏 진입을 차단하였다.

해당 거래는 A에서 +10.0 USD의 익절로 종료되었다.

B는 이후 별도의 가정 거래에서 익절이 발생했지만 일일 손익은 A -5.0 USD, B -7.5 USD로 B가 낮았다.

그러나 다음 사항으로 인해 이를 A 전략의 우수성으로 결론 내릴 수 없다.

1. A는 실제 모의계좌 체결 결과를 기록하고 B는 가정 체결을 적용한다.
2. A에는 복구 포지션 관련 청산 손익이 포함되어 있다.
3. 주문 취소·청산 처리 및 포지션 동기화 과정에서 예외가 기록되었다.
4. 거래 건수와 분석 기간이 제한적이다.
5. 체결 가격과 슬리피지 등 실행 품질의 차이가 전략 신호 차이와 혼합될 수 있다.

따라서 실시간 비교에서는 누적손익 외에 정상적인 신호 생성 여부, 주문·체결 확인 및 위험관리 작동 여부를 함께 평가한다.

## 7. 결과 해석과 한계

### 7-1. 전략 A/B 비교에 대한 종합 해석

이번 과제의 핵심 가설은 다음과 같다.

**EMA 9/21 교차 전략에 ATR 변동성 필터를 추가하면 불리한 시장 환경에서 발생하는 진입 신호를 차단하여 매매 판단의 품질을 높일 수 있다.**

최초 리플레이에서는 B가 A보다 40.0 USD 낮은 손익을 기록했으나, 추가 리플레이의 잠정 집계에서는 B가 5.0 USD 높은 손익을 기록하였다.

이는 ATR 필터가 모든 시장에서 일관된 효과를 보이지 않았음을 의미한다.

ATR 필터는 변동성 환경을 구분할 뿐 해당 신호의 미래 손익을 직접 예측하지 않는다. 따라서 변동성이 낮거나 높다는 이유만으로 신호를 차단하는 것이 언제나 유리한 것은 아니다.

특히 필터가 수익 거래를 차단하는 경우도 있었으므로, 필터 적용 전후의 수익률만 비교하는 방식은 충분하지 않다.

### 7-2. 필터 효과와 위험관리의 상호작용

ATR 필터는 개별 진입 신호의 채택 여부를 결정한다.

그러나 실제 전략은 일일 최대 진입 횟수 및 손실 한도라는 제약을 함께 적용한다.

따라서 하나의 거래가 차단되면 이후 진입 가능한 횟수와 손실 한도 도달 시점이 달라질 수 있다.

10/28 사례에서 B는 수익 거래를 차단한 뒤 손실 한도에 도달해 후속 수익 거래에도 진입하지 못했다.

이는 필터가 단순히 거래 한 건의 손익만 바꾸는 것이 아니라 전체 거래 경로를 변화시킬 수 있음을 보여준다.

**따라서 ATR 필터의 효과는 개별 차단 거래와 전체 전략의 손익 경로를 구분하여 평가해야 한다.**

### 7-3. 손익 구조 분석

최초 최종 설정 리플레이에서 A의 익절 거래 비율은 33.3%, B는 26.3%였다.

평균 익절과 평균 손절을 비교하면 다음과 같다.

| **지표** | **A** | **B** |
| --- | --- | --- |
| 평균 익절 | +12.1 | +9.5 |
| 평균 손절 절댓값 | 8.6 | 8.1 |
| 평균 익절 / 평균 손절 | 약 1.41배 | 약 1.17배 |

계획상 손절·익절 배수는 1.5 ATR과 2 ATR로 약 1:1.33이다.

그러나 실제 거래에서는 틱 단위 반올림 및 진입·청산 가격 차이로 계획한 비율과 달라질 수 있다.

또한 평균 익절·손절만으로 반대 교차 청산, 강제 청산 및 수수료를 모두 반영한 기대손익을 설명할 수는 없다.

따라서 실제 성과는 모든 청산 유형과 체결 비용을 포함하여 계산할 필요가 있다.

### 7-4. 일일 손실 한도의 실효성

현재 전략의 일일 손실 제한은 누적 실현손익이 -25 USD에 도달하면 신규 진입을 중단하는 방식이다.

따라서 신규 진입 직전에 손실 한도에 도달하지 않았더라도 해당 거래가 손절로 종료되면 일일 손익이 -25 USD보다 낮아질 수 있다.

실제 리플레이에서는 -27.5 USD의 일일 손실이 확인되었다.

이는 현재 설정상 가능한 결과이지만, 보다 엄격한 위험관리를 위해서는 신규 진입 전 누적 실현손익과 해당 거래의 예상 손절액을 합산해 판단하는 방식을 검토할 필요가 있다.

단, 시장가격 급변이나 체결 지연에 따른 손실 초과 가능성을 완전히 제거할 수는 없다.

### 7-5. 횡보장에서의 전략 취약성

EMA 교차 전략은 일정한 방향의 추세가 형성될 때 유리할 수 있으나, 횡보장에서는 상승·하락 교차가 반복되면서 손절이 누적될 수 있다.

10/27에는 EMA 교차가 빈번하게 발생했으며, 연속 손절과 일일 손실 한도 도달로 이어졌다.

이를 개선하기 위해 ATR 필터 외에도 추세의 강도를 판단할 수 있는 보조 조건을 검토할 필요가 있다.

가능한 후보로는 최근 일정 기간의 EMA 교차 횟수, EMA 간격, 추세 지속 시간 등이 있다.

다만 조건을 많이 추가할수록 거래 수가 줄고 과거 데이터에 과도하게 맞춰질 가능성도 있으므로 독립적인 데이터 구간에서 검증해야 한다.

### 7-6. 실시간 운영 결과의 의미

실시간 모의거래에서는 리플레이만으로 확인하기 어려운 운영 문제가 발견되었다.

대표적으로 다음과 같다.

- 미체결 청산 주문의 대기 및 취소
- 주문 취소 응답 오류
- 청산 상태가 해소되지 않은 상황
- 실제 계좌 잔고와 프로그램 내부 상태의 불일치 가능성
- 재시작 후 기존 포지션 복구
- 복구 거래가 성과 집계에 미치는 영향

이는 단순히 전략의 수익성만 평가해서는 자동매매 시스템의 품질을 충분히 설명할 수 없음을 보여준다.

정상적으로 수익을 기록했더라도 주문·체결·잔고가 정확하게 관리되지 않았다면 해당 결과의 신뢰성은 낮아질 수 있다.

반대로 손실을 기록한 거래라도 사전에 정의한 진입·청산 및 위험관리 절차가 정확하게 수행되었다면 실행 품질 측면에서는 긍정적으로 평가할 수 있다.

### 7-7. 검증의 한계

**① 분석 기간과 표본의 제약**

최초 리플레이는 5거래일, 추가 리플레이는 4거래일에 불과하다. 거래 수가 적어 전략 간 성과 차이가 통계적으로 유의미하다고 주장하기 어렵다.

**② 리플레이 체결 가정**

리플레이는 과거 분봉을 이용해 가상 체결을 계산하므로 실제 호가, 거래량, 체결 지연 및 미체결 상황을 완전히 반영할 수 없다.

**③ B 전략의 가상 체결**

B는 실제 주문을 내지 않으므로 B에만 발생하는 거래에는 가정 체결이 필요하다. 따라서 B의 손익은 실제 모의계좌 실현손익과 동일한 성격이 아니다.

**④ 실시간 성과 집계**

복구 포지션의 청산 손익이 포함된 기록이 확인되었다. 정상 신규 거래와 복구 거래를 구분한 뒤 성과를 재집계해야 한다.

**⑤ 주문 안정성**

청산 주문 대기·취소 과정에서 예외가 발생했으며 일부 상태의 최종 처리 결과가 확인되지 않았다.

**⑥ 수수료와 실제 거래 비용**

이번 과제에서는 수수료를 손익 계산에서 제외하였다. 따라서 결과는 실제 거래 비용을 모두 반영한 최종 수익이 아니다.

**⑦ 과최적화 가능성**

동일한 과거 데이터를 반복적으로 활용하여 ATR 범위와 전략 조건을 조정할 경우 특정 기간에만 유리한 설정을 선택할 위험이 있다.

- 주문 상태와 잔고의 최종 일치 여부 검증

**8-2-2. 포지션 상태 불일치 가능성**

실시간 실행 중 프로그램 내부 포지션 상태와 계좌의 잔여 포지션이 일치하지 않는 것으로 보이는 기록이 확인되었다.

특히 내부 상태가 IN_LONG인 상황에서 실제 잔여 포지션이 없는 것으로 나타나는 경우는 추가 검증이 필요하다.

관련 이벤트로는 POSITION_LEFT, POSITION_MISMATCH, ALREADY_FLAT 등의 상태 확인 및 오류 코드가 정의되어 있다.

**가능한 원인**

- 청산 체결 후 내부 상태 갱신 지연
- 주문 체결 확인 응답 지연
- 재시작 후 포지션 복구 과정의 상태 불일치
- 주문 조회와 잔고 조회의 시점 차이

현재로서는 원인 중 하나를 확정할 수 없다.

**개선 방향**

실제 계좌 잔고를 재확인하고 내부 포지션 상태와 대조하여, 불일치가 해소되기 전에는 신규 진입을 제한하는 방식이 필요하다.

**8-2-3. 재시작 후 복구 포지션 손익 집계**

11/04 A 전략에서는 restored: true로 표시된 포지션의 +77.5 USD 청산 손익이 확인되었다.

그러나 이를 현재 실행에서 발생한 신규 진입 성과와 혼합하면 전략 성과가 왜곡될 수 있다.

**개선 방향**

- 복구 포지션 여부를 성과 집계에 별도 표시
- 최초 진입 주문과 복구된 포지션의 연결 관계 확인
- 복구된 포지션의 청산 손익 별도 집계
- 전체 계좌 손익과 신규 전략 거래 손익을 분리

**8-2-4. 실시간 결과와 리플레이 결과의 차이**

실시간 모의거래에서는 실제 주문 처리 시간이 존재하며, 주문이 즉시 체결되지 않거나 청산 주문 취소가 필요한 상황이 발생할 수 있다.

반면 리플레이는 가정된 체결 방식으로 매매 결과를 계산한다.

따라서 두 환경의 손익 차이를 모두 전략의 우수성 또는 열위로 해석하는 것은 적절하지 않다.

실행 품질을 별도 항목으로 구분하여 평가할 필요가 있다.

### 8-3. 전략 및 시스템 개선사항

**① ATR 필터 재검증**

ATR 범위 0.90~1.30이 다양한 시장 상황에서 유효한지 추가 검증한다.

필터를 단순히 좁히는 방식보다, 차단된 거래의 사후 결과와 전체 거래 경로에 대한 영향을 비교하여 적정 조건을 판단한다.

**② 추세 강도 필터 검토**

횡보장에서 EMA 교차가 반복되는 문제를 개선하기 위해 최근 교차 횟수 및 EMA 간격 등의 추가 조건을 검토한다.

**③ 일일 손실 한도 강화**

누적 실현손익뿐 아니라 신규 거래의 예상 손절액을 반영해 진입 가능 여부를 판단하는 방식으로 개선한다.

**④ 주문 및 청산 안정성 개선**

청산 주문의 접수·미체결·취소·체결 여부를 정확히 추적하고, 실제 잔고와 프로그램 내부 포지션을 지속적으로 동기화한다.

**⑤ 신규 거래와 복구 거래 분리**

성과 집계 시 정상 신규 진입, 복구 포지션 및 가정 체결을 구분한다.

**⑥ 실행 품질 지표 도입**

매매 손익 외에도 주문 지연, 체결 확인 시간, 슬리피지, 취소 오류, 청산 경고 및 포지션 불일치 발생 여부를 평가한다.

**⑦ ATR 필터의 판단 근거 기록**

B 전략에서 거래를 차단한 경우, 해당 시점의 ATR 비율과 차단 사유를 기록하고 차단된 거래의 가상 결과를 함께 분석한다.

이는 단순히 거래하지 않았다는 사실이 아니라, **거래하지 않은 판단이 적절했는지** 평가하기 위한 것이다.

**⑧ 성과 집계 기준 표준화**

| **손익 구분** | **내용** |
| --- | --- |
| 전체 기록 손익 | 저널에 기록된 전체 청산 손익 |
| 신규 전략 거래 손익 | 신규 진입부터 청산까지 정상적으로 추적된 거래 |

| 가정 체결 손익 | 리플레이 또는 B 재계산 결과 |
| 실제 비용 반영 손익 | 수수료 및 기타 거래 비용을 반영한 손익. 이번 과제의 기본 집계에서는 별도 산출하지 않음 |

이와 같은 분류를 통해 전략 신호의 성과와 프로그램의 실행 결과를 구분하고, A/B 비교의 신뢰성을 높인다.

## 9. 향후 계획

### 9-1. 필터 효과 검증 체계 개선

ATR 필터 적용 후 누적손익이 증가했는지만 평가하는 것이 아니라, 필터가 차단한 거래의 수와 결과를 함께 분석한다.

특히 다음 네 가지를 구분한다.

1. 손실 거래를 차단한 경우
2. 수익 거래를 차단한 경우
3. 필터 적용으로 이후 진입 기회가 변경된 경우
4. 필터 적용으로 손실 한도 도달 시점이 달라진 경우

이를 통해 필터의 판단 품질을 보다 구체적으로 평가한다.

### 9-2. 리스크 관리 정교화

기존 일일 손실 제한 및 진입 횟수 제한에 더해 다음 사항을 검토한다.

- 진입 전 예상 손절 금액 확인
- 청산 주문 미체결 시 안전 조치
- 실제 잔고와 내부 포지션 불일치 시 신규 진입 중단
- 프로그램 재시작 후 보유 포지션 확인
- 반복 주문 오류 발생 시 경고 및 안전 정지

### 9-3. 실시간 실행 안정성 개선

모의계좌 주문·체결·잔고의 상태를 정확히 추적하고, 주문 지연 및 취소 실패 등 정상적이지 않은 상황에서도 위험 노출을 관리할 수 있도록 개선한다.

특히 주문 상태 불일치와 복구 포지션 문제를 우선 점검한다.

### 9-4. 성과 평가 기준 확대

단순 누적손익과 승률뿐 아니라 다음 요소를 함께 평가한다.

- 신호 발생 및 실제 진입 비율
- 필터에 의한 차단 거래 비율
- 차단으로 회피한 손실 및 놓친 수익
- 평균 익절·손절 및 손익비
- 최대 낙폭
- 슬리피지와 주문 지연
- 오류 및 상태 불일치 발생 빈도
- 계획된 거래 규칙의 준수 여부

### 9-5. 검증 기간 확대

현재 분석은 제한된 야간장 데이터에 기반하므로 추가적인 거래일을 확보해 검증할 필요가 있다.

특히 추세장과 횡보장, 변동성이 높은 구간과 낮은 구간을 구분하여 동일한 전략의 안정성을 평가한다.

ATR 필터 범위를 선정한 데이터와 성과를 평가하는 데이터를 분리하여 과최적화 위험을 줄인다.

### 9-6. 최종 개발 방향

본 프로젝트는 높은 수익률을 달성하는 전략을 만드는 것만을 목표로 하지 않는다.

**매매 의사결정의 신뢰성과 정교함을 높이고, 거래의 전 과정을 검증할 수 있는 자동매매 시스템을 구축하는 것을 핵심 방향으로 설정하였다.**

이를 위해 다음 과정을 하나의 검증 체계로 연결한다.

**시장 데이터 수집 → 매매 신호 생성 → 신호 품질 검증 → 진입 또는 거래 보류 → 위험관리 → 주문 실행 → 체결 확인 → 결과 분석**

특히 거래하지 않은 판단과 그 사유까지 기록하여, 단순한 매매 결과뿐 아니라 의사결정 과정 자체를 평가할 수 있도록 개선한다.

궁극적으로 다음 질문에 객관적으로 답할 수 있는 시스템을 지향한다.

- 왜 해당 시점에 진입했는가?
- 왜 특정 신호에서는 거래하지 않았는가?
- 설정한 위험관리 규칙이 실제로 작동했는가?
- 프로그램이 주문과 체결을 정확하게 처리했는가?
- 기록된 손익을 신뢰할 수 있는가?
- 다음 거래에서 무엇을 개선해야 하는가?

## 최종 결론

이번 3주차 과제에서는 SGX 미니 원달러 선물에 EMA 9/21 교차 전략을 적용하고, ATR 변동성 필터를 추가한 A/B 전략을 비교하였다.

최초 리플레이에서는 B 전략이 A보다 낮은 성과를 기록했으나, 추가 리플레이의 잠정 결과에서는 B가 일부 손실 거래를 차단하는 효과를 보였다.

이러한 결과는 ATR 필터가 항상 수익성을 개선하는 것은 아니며, 필터의 효과가 시장 상황과 위험관리 조건에 따라 달라질 수 있음을 보여준다.

실시간 모의거래에서는 리플레이로 확인하기 어려운 주문 대기·취소, 포지션 상태 불일치 가능성, 재시작 후 복구 포지션 등의 문제가 확인되었다.

이를 통해 **전략의 수익성뿐 아니라 주문 실행의 안정성과 성과 집계의 정확성이 자동매매 시스템의 신뢰성을 결정한다는 점**을 확인하였다.

따라서 향후에는 전략의 수익률을 높이는 데만 집중하기보다, 매매 신호의 유효성을 검증하고 거래하지 않는 판단까지 기록하며, 주문 및 위험관리 과정의 안정성을 높이는 방향으로 개선하고자 한다.

이번 과제의 핵심 성과는 단순히 수익이 발생했다는 사실이 아니라, **매매 판단과 실행 과정의 문제를 확인하고 그 원인과 개선 방향을 설명할 수 있는 검증 체계를 구축하기 시작했다는 점**에 있다.
